# Studio Worker Provider — Rakazo pilot

This isolated pilot extends the existing Nuwa Remote MCP without changing the original Fleet Gateway, Worker Gateway or the message Inbox transport.

## Boundary

The remote assistant discovers approved tools through the ordinary Nuwa MCP endpoint. Studio alone reads the Windows user's protected Worker credential and invokes the fixed local `http://127.0.0.1:3791/mcp`. The shared `worker-provider.json` allowlist limits both cloud and local execution. The Gateway remains authoritative for project/model selection, workspaces, Job state, Git policy and delivery. The original Session Router Skill remains the routing policy.

The first transport is a dedicated authenticated HTTPS long-poll request/result channel, backed by a Cloudflare Durable Object per remote OAuth grant. A Studio request waits up to 20 seconds for work; no idle periodic cloud-to-local HTTP request or public local port is needed. Tool results are correlated with one outstanding request. A tool call times out after 45 seconds; the Studio never automatically replays a command after a transport failure. The original Gateway requestId is preserved for its idempotency contract.

## Windows setup and use

1. Install T3 Code and AI Worker Gateway on a dedicated Windows test Worker. Install Nuwa Studio using Windows Setup. Setup registers the optional windowless, current-user Worker task; it is inactive until paired. Existing Nuwa identity and messaging registrations remain intact.
2. Connect Rakazo to the normal Nuwa Remote MCP using a **dedicated OAuth connection assigned only to the test assistant**. Install the canonical [Session Router Skill](https://mcp.agent-relay.company-notes.com/skills/session-router/SKILL.md).
3. Ask Rakazo to connect the local Worker. It invokes `worker_provider_pair` and returns a clickable `authorizationURL` and a separately copyable one-time code. The owner opens the link in their browser on the Windows Worker, clicks **Open Nuwa Studio**, and approves the browser's application prompt if required. The installed protocol handler starts the same local authorization page as Windows Start → Nuwa Studio → Connect Worker. No Computer Use or assistant-initiated browser operation is required.
4. The owner enters the code directly on the local page, confirms the displayed scope, and completes the ordinary Nuwa sign-in if required. The selected grant can use every approved tool and visible Job of the dedicated Gateway; per-assistant and per-Job controls for shared gateways remain future work. The code expires in five minutes.
5. Studio starts its installed background task automatically. Rakazo verifies `worker_provider_status`, refreshes the MCP catalog, and performs read-only discovery before dispatch. Ask Rakazo to build a marketing tracker and add monthly ROAS to the same Job. Verify the actual Job and deliverable. Routine progress queries remain available. Completion notifications use the existing Gateway notification tools and the same paired Studio connection; see below.
6. The task resumes an existing authorized binding at Windows sign-in and independently of desktop AI client windows. When the local Gateway is unavailable, the catalog is empty; discovery resumes when it returns. Network interruptions do not automatically replay an uncertain dispatch. Reuse the original Gateway requestId and inspect existing work.
7. Revoke remotely using `worker_provider_revoke` with owner approval, or use the local administrative `worker revoke` command. Uninstall stops and removes the owned startup task without deleting existing Nuwa identity files or T3 Jobs. Upgrade drains the active Worker exchange before replacing the Worker executable; a busy native MCP still uses the existing update-deferred flow.

## Optional completion notifications

Upgrade the [AI Worker Gateway Windows installation](https://github.com/company-notes/ai-worker-gateway/blob/main/docs/windows-install.md) to include the notification browser fix, then install Nuwa Studio 0.2.13 or later. Preserve the existing settings, identities and Worker pairing. After the Gateway and Studio are upgraded, refresh the assistant's MCP catalog and update both official Skills. No new Worker pairing or OAuth grant is required. Installation verifies Worker pairing and availability only. The assistant dispatches the first requested Job before offering notifications, privately retains its notificationSetupToken, and asks once if the preference is unset. If the owner opts in, it creates and verifies the actual platform's webhook receiver before calling worker_notification_setup with that token and giving the owner the returned local URL and directions to the receiver credentials. The owner opens the form on the Windows Worker and enters the receiver URL, header and key there, with no assistant name. Studio forwards only approved notification tools and private route/setup handles, never webhook URL or key arguments. Gateway owns the form, encrypted settings, per-Job binding, work_feed polling, delivery, and retry queue. The receiver must verify and actually present test and completion events.

Use the [Rakazo guide](https://mcp.agent-relay.company-notes.com/skills/nuwa-agent-relay/references/rakazo.md) for a dedicated webhook-only Routine; other clients use their own supported notification receiver. The existing Gateway route is a bearer capability and must be retained privately by the assistant. The dedicated OAuth pilot is not multi-assistant or per-Job access isolation. Disabling a notification route and revoking a Worker connection are separate operations; existing Gateway callbacks may continue until their route is disabled. New routed Jobs and continuations inherit the configured notification behavior; The first Job is bound on successful pairing using its short-lived dispatch capability; arbitrary older Jobs cannot be retroactively assigned.

## Platform and acceptance

The Windows service uses a separate GUI-subsystem executable and a current-user Task Scheduler logon task, with no administrator privilege or exposed local port. The local authorization page is loopback-only, uses an unpredictable path and accepts same-origin form submissions. Pairing codes are not URLs, command-line arguments or logs. The official public landing page contains no code or credentials; the installed current-user protocol handler launches the fixed pairing command without forwarding the URL. The assistant must leave opening the link, code entry and confirmation to the owner.

The current AI Worker Gateway credential contract is Windows DPAPI. macOS and Linux retain their existing Studio messaging support; Worker service installation for those systems requires a supported local Gateway credential contract and verified launchd/systemd user-service integration. No non-Windows service is registered by this release.

The final release gate is the real Rakazo-to-T3 flow, including authorization, start/continue, delivery, notification consent/test/receipt, independent Studio startup, recovery and revocation. The dedicated pilot does not grant per-Job access isolation.
